# STD-005 - Database Standard
Status: PROPOSED
Revision 1.3 (2026-10-19): aligned with ADR-0020..0027 (adopted Debezium outbox with `wal_level=logical`, Vault dynamic PostgreSQL credentials, Redis key/TTL rules, Qdrant collections, Temporal persistence boundaries).
Version: 1.3
Date: 2026-10-19
Applies to: every PostgreSQL database owned by a WAVER service, plus the Redis keyspaces and Qdrant collections a service owns (BFF sessions now live in Redis, ADR-0020)
Related: ADR-0003, ADR-0010, ADR-0020, ADR-0022, ADR-0023, ADR-0024, ADR-0025, AR-002, AR-005, AR-012, AR-013, CONVENTIONS (Database), RFC-0003, RFC-0006, RFC-0007, RFC-0014, STD-001, STD-004, STD-010, STD-014

Keywords MUST, MUST NOT, SHOULD follow RFC 2119. Topology, backups and lifecycle design are in RFC-0007; this standard lists the rules every schema, query, key and collection is checked against. PostgreSQL remains the source of truth for every business fact; Redis and Qdrant hold only rebuildable or disposable data (ADR-0020, ADR-0025), and Temporal's database belongs to Temporal (D-42).

## 1. Ownership and naming
- **D-01** One database per service, `waver_<service>` (CONVENTIONS). A service MUST NOT read or write another service's database by any means (shared credentials, `dblink`, `postgres_fdw`, shared schemas, views, replication into its own DB) (AR-002). Other services' data comes from APIs or event-fed read models. The only external reader of a service database is its Debezium connector, limited to `outbox_event` (§11).
- **D-02** Tables and columns `snake_case`; tables singular (`contract_item`); PK `id`; FK `<referenced_table>_id`. Read models are prefixed `rm_` and carry `source_aggregate_id`, `source_version`, `updated_at`.
- **D-03** Constraint/index names: `pk_<table>`, `fk_<table>__<ref_table>`, `ux_<table>__<cols>`, `ix_<table>__<cols>`, `ck_<table>__<rule>`. RLS policies: `tenant_isolation` (standard), descriptive names for audited cross-tenant policies (`reseller_portfolio`, `platform_oversight`).
- **D-04** Roles per database (RFC-0007 §2): `<svc>_owner` (NOLOGIN, owns objects), `<svc>_migrator` (NOLOGIN group, used by the Flyway Job), `<svc>_app` (NOLOGIN group for pods: DML only, not owner, **no BYPASSRLS**), `<svc>_cdc` (LOGIN `REPLICATION`, `SELECT` on `outbox_event` only, used by Debezium; replaces the v1.2 `<svc>_relay`), `<svc>_xtenant` (NOLOGIN group, read-only, only in services owning audited cross-tenant views). Pods and Jobs never log in as these group roles: Vault creates short-lived login users that are members of them (D-29). Session limits are set on every login user by the Vault creation statements, because `ALTER ROLE ... SET` on a group is not inherited: `statement_timeout` 5 s for `_app`, 60 s for `_xtenant`; `idle_in_transaction_session_timeout` 30 s.

## 2. Column types and mandatory columns
- **D-05** Every aggregate table has `id uuid` (UUIDv7 generated by the application), `org_id uuid` if tenant-owned (+ `workspace_id`, `domain_id` when scoped), `created_at timestamptz`, `created_by uuid`, `updated_at timestamptz`, `updated_by uuid`, `version bigint` (optimistic lock, source of the HTTP `ETag`).
- **D-06** Time is `timestamptz` (UTC); calendar dates are `date`. `timestamp without time zone` is forbidden. (The CloudEvents header columns of `outbox_event` are pre-formatted `text`, §11.)
- **D-07** Money is `numeric(19,4)` plus a `char(3)` currency column. `real`, `double precision` and `money` are forbidden for monetary values.
- **D-08** Enumerations are `text` + `CHECK` constraint (no PostgreSQL `ENUM` types). Booleans are `NOT NULL` with a default. Every new column carries a classification comment: `COMMENT ON COLUMN t.c IS 'class=CONFIDENTIAL;pii=false'`.

```sql
CREATE TABLE contract_item (
  id            uuid          NOT NULL,
  org_id        uuid          NOT NULL,
  contract_id   uuid          NOT NULL,
  sku_id        uuid          NOT NULL,
  quantity      integer       NOT NULL,
  unit_price    numeric(19,4) NOT NULL,
  unit_price_currency char(3) NOT NULL,
  status        text          NOT NULL,
  effective_from date         NOT NULL,
  created_at timestamptz NOT NULL, created_by uuid NOT NULL,
  updated_at timestamptz NOT NULL, updated_by uuid NOT NULL,
  version    bigint      NOT NULL DEFAULT 0,
  CONSTRAINT pk_contract_item PRIMARY KEY (id),
  CONSTRAINT fk_contract_item__contract FOREIGN KEY (contract_id) REFERENCES contract (id),
  CONSTRAINT ck_contract_item__quantity CHECK (quantity > 0),
  CONSTRAINT ck_contract_item__status CHECK (status IN ('PENDING','ACTIVE','SUSPENDED','CANCELLED'))
);
CREATE INDEX ix_contract_item__org_id_contract_id ON contract_item (org_id, contract_id);
COMMENT ON COLUMN contract_item.unit_price IS 'class=CONFIDENTIAL;pii=false';
```

## 3. Row-Level Security (ADR-0010, RFC-0007 §3)
- **D-09** Every table with `org_id` has `ENABLE` **and** `FORCE ROW LEVEL SECURITY` and a `tenant_isolation` policy in the same migration that creates it. Tables without `org_id` are listed with justification in `db/platform-tables.txt`.
- **D-10** The platform starter sets context per transaction with `set_config(..., true)`: `waver.org_id`, `waver.org_type`, `waver.workspace_id` (`''` when org-wide), `waver.domain_id` (`''` when not domain-scoped). Policies MUST wrap settings in `NULLIF(..., '')` so a missing context yields zero rows, never all rows or a swallowed error. Policies are written `TO <svc>_app` / `TO <svc>_xtenant` (group roles); they apply to the Vault-issued members through role membership.

```sql
ALTER TABLE agent ENABLE ROW LEVEL SECURITY;
ALTER TABLE agent FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON agent
  USING (
    org_id = NULLIF(current_setting('waver.org_id', true), '')::uuid
    AND (NULLIF(current_setting('waver.workspace_id', true), '') IS NULL
         OR workspace_id = NULLIF(current_setting('waver.workspace_id', true), '')::uuid)
    AND (NULLIF(current_setting('waver.domain_id', true), '') IS NULL
         OR domain_id = NULLIF(current_setting('waver.domain_id', true), '')::uuid))
  WITH CHECK (org_id = NULLIF(current_setting('waver.org_id', true), '')::uuid);

-- audited cross-tenant path (only in services owning the view), role _xtenant, local read model
CREATE POLICY reseller_portfolio ON contract FOR SELECT TO contract_xtenant
  USING (org_id IN (SELECT customer_org_id FROM rm_org_relationship
                    WHERE reseller_org_id = NULLIF(current_setting('waver.org_id', true), '')::uuid
                      AND status = 'ACTIVE'));
```
- **D-11** The `_xtenant` datasource is used only by query handlers annotated `@CrossTenantQuery`, which emit an audit event per query (AR-009). `USING (true)` policies are forbidden; WAVER oversight uses an explicit `PLATFORM` org-type condition.

## 4. Indexes
- **D-12** Every FK column is indexed. Tenant-owned indexes lead with `org_id` (then `workspace_id`) unless a measured plan proves otherwise. Per-tenant uniqueness includes `org_id`.
- **D-13** Soft-deleted tables use partial indexes `WHERE deleted_at IS NULL` for uniqueness and hot queries.
- **D-14** Indexes on existing tables are created with `CREATE INDEX CONCURRENTLY` in a dedicated migration with `executeInTransaction=false`.
- **D-15** No vector columns or vector indexes in PostgreSQL: embeddings are stored in Qdrant (ADR-0025, §10); PostgreSQL keeps documents, chunk text, metadata and permissions, with full-text indexes (`tsvector` + GIN) where hybrid retrieval needs them.

## 5. Migrations (Flyway)
- **D-16** Flyway, forward-only, `V<yyyyMMddHHmm>__<description>.sql` in `services/<svc>/<svc>-adapters/src/main/resources/db/migration`. Applied migrations are never edited; a bad migration is fixed by a new one.
- **D-17** Migrations run as the Kubernetes Job `<svc>-migrate` (Helm pre-upgrade hook, RFC-0014 §5) with a Vault-issued user that is a member of `<svc>_migrator` (Vault role `<service>-migrate`). Flyway runs with `initSql: SET ROLE <svc>_owner` so every object is owned by `<svc>_owner`, never by the short-lived login user (otherwise revoking the user would fail or orphan objects). Pods run with `spring.flyway.enabled=false` in staging/production and `spring.jpa.hibernate.ddl-auto=validate`.
- **D-18** Every schema change is compatible with releases N and N+1 (rolling deploys). Breaking changes use **expand/contract**: add nullable column / new table and dual-write → backfill → switch reads → drop old structures in a later release. Backfills over 10 000 rows run as idempotent keyset batch jobs (or Temporal workflows when they must survive restarts, RFC-0014 §5), never inside a migration.
- **D-19** Each migration sets `lock_timeout = '5s'` and a `statement_timeout`; `NOT NULL` is added via `CHECK ... NOT VALID` + `VALIDATE`; column type changes and drops of columns still used by N are forbidden. Changes to `outbox_event` columns read by the Outbox Event Router are contract migrations released together with the connector configuration (RFC-0014 §5).

## 6. JSONB
- **D-20** JSONB is allowed for versioned documents read and written as a whole: draft sections, flow definitions, runtime artifacts, connector manifests, tool schemas, policy documents, UI settings. Each document carries a `schemaVersion` and is validated against its JSON Schema in the application. (Outbox payloads are Avro `bytea`, §11.)
- **D-21** JSONB MUST NOT hold `org_id`/scope keys, data used for joins, authorization filters, billing aggregation or money. GIN indexes only for proven query patterns.

## 7. Soft delete, retention and purge (AR-012, RFC-0007 §9)
- **D-22** `deleted_at`/`deleted_by` only where retention requires recoverability. Suspension and termination never delete or soft-delete data.
- **D-23** Hard deletion of tenant data happens only through the service's `DataLifecyclePort.purge` (idempotent, resumable, approved via approval-service, audited, verified by post-purge counts), which also removes `rm_*`, outbox and idempotency rows of that org, the org's Qdrant points (`delete` by `org_id` filter, §10) and the org's tenant-scoped Redis keys (§9). The purge runs as a Temporal workflow of tenant-service orchestrating each owner's purge API (ADR-0023).
- **D-24** Large objects go through `ObjectStoragePort` (v1 adapter: RLS-protected `blob_object` table, ≤ 20 MB per object), never ad-hoc `bytea` columns in business tables.

## 8. Query performance, pools and Vault credentials
- **D-25** No unbounded queries: every list query has a `LIMIT` and uses keyset pagination. `spring.jpa.open-in-view=false`; no lazy loading across aggregate boundaries; N+1 avoided with fetch joins, projections or `JdbcClient` SQL (allowed for hot paths, bulk writes, read models, full-text queries).
- **D-26** One aggregate per transaction; default isolation `READ COMMITTED`; pessimistic locks only for `FOR UPDATE SKIP LOCKED` work queues. PostgreSQL advisory locks are not used for coordination: timers and singleton processes are Temporal workflows (ADR-0023), short cross-pod coordination uses the Redis `DistributedLockPort` (ADR-0020, STD-001 J-47), and correctness always rests on optimistic locking.
- **D-27** Queries slower than 500 ms are logged without bind values; new queries on tables expected to exceed 1 M rows include an `EXPLAIN (ANALYZE, BUFFERS)` from a representative synthetic dataset in the PR.
- **D-28** Connections use TLS (`sslmode=verify-full`). Pool defaults (HikariCP, Spring Boot default):

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # per pod (RFC-0007); virtual threads do not change this (STD-001 J-27)
      minimum-idle: 10             # fixed-size pool
      connection-timeout: 2000     # ms; fail fast -> 503 DEPENDENCY_UNAVAILABLE
      max-lifetime: 1800000        # 30 min; MUST stay below the Vault credential TTL (D-29)
  jpa:
    open-in-view: false
    hibernate.ddl-auto: validate
    properties.hibernate.jdbc.batch_size: 50
  flyway.enabled: false            # staging/production: migrations run in the Job (D-17)
  cloud:
    vault:
      database: { enabled: true, role: contract-app, backend: database }   # Vault role <service>-app
      config.lifecycle:
        min-renewal: 10s
        expiry-threshold: 35m       # rotate before expiry by more than max-lifetime + margin
```
`max replicas × maximum-pool-size` per service stays within its `max_connections` budget in `deploy/environments/<env>`; the budget also reserves one replication connection per producing database for Debezium and the migrate Job's connections.

- **D-29** **Dynamic credentials (ADR-0022)**: pods obtain PostgreSQL credentials from the Vault database secrets engine through Spring Cloud Vault (role `<service>-app`, default TTL 1 h, renewed; bounded max TTL). Rules:
  - Vault creation statements create a `LOGIN` user `IN ROLE <svc>_app` with `VALID UNTIL '{{expiration}}'` and set its session limits (D-04); revocation statements run `REASSIGN OWNED BY "{{name}}" TO <svc>_owner; DROP OWNED BY "{{name}}"; DROP ROLE "{{name}}"`.
  - No pooled connection may outlive its credential: `max-lifetime` (30 min) < TTL (1 h), and when Spring Cloud Vault rotates the credential (`expiry-threshold` reached or renewal refused) the platform starter sets the new username/password on the pool (`HikariConfigMXBean`) and calls `softEvictConnections()`, so new connections use the new user while in-flight work finishes.
  - If Vault is unavailable, running pods keep working until their current lease expires, renewal failures raise an alert (STD-007), and new pods do not become ready. Credentials are never cached on disk or in environment variables.
  - The migrate Job (D-17) and the Debezium `<svc>_cdc` user obtain their credentials from Vault the same way (roles `<service>-migrate`, and the platform's CDC role); no static database passwords exist outside Vault.

## 9. Redis keys and TTL (ADR-0020)
- **D-30** Keys follow `waver:<prefix>:<name>:<...>` with the prefixes of ADR-0020: `sess:<bff>` (BFF sessions), `quota` (usage-metering-service), `idem:<service>`, `cache:<service>:<name>`, `lock:<service>`, `run-stream` (agent-runtime). Each service's Redis ACL user is restricted to its own prefixes (`~waver:<prefix>:*`) with a command allow-list (no `KEYS`, `FLUSHDB`, `FLUSHALL`, `CONFIG`, `DEBUG`); no service reads another service's keys. Tenant-scoped keys put the organization right after the name (`waver:cache:catalog-service:price-book:<orgId>:<id>`) so purge (D-23) and diagnostics can address one org with `SCAN MATCH`.
- **D-31** Every key has a TTL set on write (`SET ... EX`, `EXPIRE` in the same Lua script or pipeline). Defaults: sessions = Spring Session idle timeout (RFC-0004); idempotency 24 h (endpoints documenting a longer window up to 7 d, CONVENTIONS); shared caches ≤ 15 min with event-driven eviction; quota counters until period end + 24 h; locks ≤ 30 s; run streams 15 min with `XADD ... MAXLEN ~ <n>`. Keys without TTL are a defect (detected by the Redis test kit, STD-010).
- **D-32** Keys contain only IDs — never PII, e-mails, names, tokens or free text. Values avoid PII; a value that must contain personal data (BFF session attributes) is limited to what the session needs and expires with it. Values are ≤ 100 KiB; larger data stays in PostgreSQL or object storage.
- **D-33** Redis is never authoritative: quota counters are reconciled to PostgreSQL `quota_counter` every minute and PostgreSQL wins for billing; idempotency records needed for audit are also stored in PostgreSQL; losing the whole keyspace must cause only degradation (ADR-0020). Redis Cluster hash tags (`{...}`) are used only when a Lua script must touch several keys atomically, and never on the org ID alone (hot slots for large tenants).

## 10. Qdrant collections and payloads (ADR-0025)
- **D-34** Collections are owned by one service and named `<entity>_v<N>` (`knowledge_chunks_v1`, `memory_entries_v1`); code always uses the alias `<entity>` (`knowledge_chunks`). Each collection definition (vector size and distance per embedding model, HNSW and payload-index configuration) is versioned in `services/<svc>/<svc>-adapters/src/main/resources/qdrant/<entity>_v<N>.json` and applied idempotently by the `<svc>-migrate` Job. A new embedding model or vector size means a new `_v<N+1>` collection filled by a Temporal ingestion workflow and switched by an atomic alias swap after verification (point count and sample checks against PostgreSQL); collections are never altered in place.
- **D-35** Point ID = the PostgreSQL row ID (`chunk_id`, `memory_entry_id`), so writes are idempotent upserts. The payload holds only filter fields: `org_id`, `workspace_id`, `domain_id`, `knowledge_base_id` (knowledge), `chunk_id`/`memory_entry_id`, `acl_tags`, `embedding_model`. Chunk text, document titles, PII and any other content stay in PostgreSQL. `org_id` has a keyword payload index with `is_tenant: true`; `workspace_id`, `domain_id`, `knowledge_base_id` and `acl_tags` have keyword indexes.
- **D-36** Every search, scroll, count and delete carries the mandatory filter built by the platform tenant-filter helper from `TenantContext` (STD-001 J-45); permission filters are applied inside the vector search, before ranking. Every hit is re-checked against PostgreSQL (row exists, not deleted, permitted under RLS) before it is used; Qdrant results are candidates, not facts.
- **D-37** Collections are rebuildable from PostgreSQL at any time (quarterly rebuild drill, ADR-0025); dual writes are reconciled by the ingestion workflow. Each service uses its own Qdrant API key (from Vault) restricted to its collections.

## 11. Outbox table for Debezium (ADR-0024)
- **D-38** Each producing service has one `outbox_event` table created by the platform migration template. Columns are exactly those read by the Outbox Event Router; header columns are `text` pre-formatted by the platform publisher (RFC 3339 UTC time, decimal version) so connector converters never reformat them:

```sql
-- Authoritative DDL: RFC-0006 (copied verbatim; change it there first)
CREATE TABLE outbox_event (
  seq                 bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  id                  uuid        NOT NULL,              -- = ce_id; repeated only by an audited republish (§10)
  org_id              uuid,                              -- null only for platform-wide events (RLS on insert, RFC-0007)
  aggregate_type      text        NOT NULL,
  aggregate_id        uuid        NOT NULL,              -- Kafka key (customer orgId for entitlement-snapshot)
  topic               text        NOT NULL,              -- routing target (route.by.field)
  payload             bytea,                             -- Avro data, Confluent wire format; NULL = tombstone (state topics only)
  schema_id           int,                               -- registry ID embedded in payload (diagnostics)
  content_type        text        NOT NULL DEFAULT 'application/avro',
  ce_specversion      text        NOT NULL DEFAULT '1.0',
  ce_type             text        NOT NULL,
  ce_source           text        NOT NULL,
  ce_subject          text        NOT NULL,
  ce_time             text        NOT NULL,              -- RFC 3339 UTC, set by the starter
  ce_dataschema       text        NOT NULL,
  ce_orgid            text        NOT NULL,
  ce_workspaceid      text,
  ce_domainid         text,
  ce_correlationid    text        NOT NULL,
  ce_causationid      text        NOT NULL,
  ce_actorid          text        NOT NULL,
  ce_actortype        text        NOT NULL,
  ce_supportgrantid   text,
  ce_aggregateversion text,
  ce_traceparent      text,
  ce_tracestate       text,
  republish_of        bigint,                            -- seq of the original row for audited republishes
  created_at          timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX outbox_event_created ON outbox_event (created_at);
CREATE INDEX outbox_event_id ON outbox_event (id);

CREATE TABLE debezium_heartbeat (id int PRIMARY KEY, ts timestamptz NOT NULL);  -- one row, see heartbeat below

-- created by the migrator role; the CDC role only reads through it
CREATE PUBLICATION waver_outbox FOR TABLE outbox_event, debezium_heartbeat;
```
The router maps `id` → event ID, `aggregate_id` → key, `payload` → value (`ByteArrayConverter`), `topic` → destination, and the `content_type` and every `ce_*` column (including `ce_type`, `ce_specversion`, `ce_traceparent`, `ce_tracestate`) → Kafka headers via `table.fields.additional.placement`; the full connector configuration is in RFC-0006 (authoritative).
- **D-39** `_app` may only `INSERT` into `outbox_event` (RLS `WITH CHECK org_id = current org OR org_id IS NULL`, RFC-0007); `<svc>_cdc` may only `SELECT` it; no service code reads, updates or deletes outbox rows. Rows are retained for 72 h (replay window for `tooling/event-replay`) and then deleted in batches by the platform cleanup job; high-volume services partition by day and drop partitions.
- **D-40** Producing databases run with `wal_level = logical`, `max_replication_slots` and `max_wal_senders` sized for one slot per producing database plus headroom, and `max_slot_wal_keep_size` set so that a stalled connector can never fill the disk. The replication slot (`waver_<svc>_outbox`) and the publication (`FOR TABLE outbox_event` only) are created by platform provisioning, not by service migrations (RFC-0014 §5). Slot lag, inactive slots and connector task failures are alerted (STD-007); if a slot is ever invalidated, recovery re-creates it and republishes the retained rows (consumers deduplicate by `ce_id`).
- **D-41** The inbox table `processed_event(consumer_group, event_id)` and `idempotency_record` are unchanged (RFC-0006, RFC-0007); the v1.2 relay columns (`seq`, `shard`, `published_at`, `attempts`) no longer exist.

## 12. Temporal persistence (ADR-0023)
- **D-42** Temporal's persistence and visibility databases belong to the Temporal cluster; no service connects to them, queries them or copies workflow state into its own tables beyond the business status of its aggregates (e.g., `provisioning_job.status`). The former `next_wakeup_at`/timer tables of v1.2 state machines are not created; timers live in Temporal. Search attributes used for operations are IDs only (no PII).

## Enforcement
| Rule | Enforced by |
|---|---|
| D-01 no cross-database access | One role set per service, `REVOKE ALL ... FROM PUBLIC`, Vault policies (a pod can only obtain `<service>-app`), NetworkPolicy + Istio `AuthorizationPolicy`; Maven Enforcer; review |
| D-02, D-03, D-05..D-08 naming/types/comments | Migration linter (ADR-0010) on `db/migration/*.sql` |
| D-04, D-29 roles and credentials | Vault database roles and policies as code (`deploy/platform/vault/`), reviewed; platform test of credential rotation with HikariCP (STD-010); no static DB passwords (secret scanning, STD-014) |
| D-09..D-11 RLS | Migration linter (`org_id` ⇒ `ENABLE`+`FORCE`+policy; no `USING (true)`); tenancy test kit (STD-010); ArchUnit: `_xtenant` datasource only in `@CrossTenantQuery` classes |
| D-14, D-18, D-19 safe migrations | Linter flags non-concurrent indexes on existing tables, `ALTER ... TYPE`, direct `SET NOT NULL`, `DROP COLUMN`, and any `outbox_event` change without a matching connector change; N/N+1 compatibility test (RFC-0007) |
| D-16, D-17 Flyway | `validateOnMigrate`; Testcontainers migration test from an empty DB on every build; check that no object is owned by a login user |
| D-23, D-24 purge / blobs | Purge/export tests per service (PostgreSQL, Qdrant and Redis); ArchUnit: `bytea` mapping only in the platform blob and outbox adapters |
| D-25..D-28 queries/pools | Starter defaults and config test; role-level timeouts; slow-query metric and alerts (STD-007) |
| D-30..D-33 Redis | `RedisKeys` helper (STD-001 J-43); ACLs in the Helm chart reviewed per service; Redis test kit asserts prefix and TTL on every key written (STD-010) |
| D-34..D-37 Qdrant | Collection definitions reviewed as code; tenancy test kit extended to Qdrant (no cross-tenant/cross-domain hit); quarterly rebuild drill |
| D-38..D-41 outbox | Platform migration template; connector configuration generated from the platform template; slot/connector alerts (STD-007); integration test through Debezium (STD-004 K-23) |
| D-42 Temporal | Network/mesh policy: only Temporal reaches its databases; review |

## Open Questions
1. ~~Database names for multi-word services~~ — resolved in the v1.2 review: underscores (`waver_agent_builder`, `waver_usage_metering`), now in CONVENTIONS.
2. The migration linter tool is not chosen (ADR-0010); proposal: a small Java checker in `waver-platform-test`.
3. Whether `created_by`/`updated_by` record the support operator or the impersonated user during support sessions; proposal: the real operator, with the grant in the audit event.
4. Managed PostgreSQL (cloud still open): logical replication slots, `max_slot_wal_keep_size` and the Vault database plugin's role-management statements must be supported by the chosen offering; confirm before the cloud ADR.
5. Outbox retention of 72 h vs. Debezium's option of deleting rows right after insert: 72 h is proposed for replay after a lost slot; confirm against storage cost for data-plane producers.
